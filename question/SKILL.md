# question

用同目录下的 `questions.md`（提问模板）质询代码或设计。

**只提问、只报告，不代劳**：给出问题、位置与严重度；除非用户明说，不要顺手改代码。

---

## 第一步 · 定模式

- **没给目标** → 「动笔前」模式：把当前正在讨论的设计，过一遍 `T1–T8` 与相关小节，说出**动笔前必须先想清楚的那几件事**。不要清单式复读全文。
- **给了目标**（路径 / 模块 / diff / PR / "刚写的这段"）→ 「扫描」模式，走下面的流程。
- **用户点名了小节**（如"用第一、五节扫"）→ 只用那几节，不要擅自扩大。

## 第一步半 · 准备扫描目标（本节是实战踩出来的，别跳）

- 仓库可能停在某个历史提交或半完成状态。**先确认要扫的是哪一版**，别扫到中间态。
- **不要在用户的工作区里 checkout**。做一个只读克隆到临时目录再切到目标提交，扫完丢掉。
- 第三节要**需求文档**：先确认它在不在版本库里。找不到就明说「第三节降级」，不要假装对照过。

## 第二步 · 选节

先读 `questions.md`。**按目标挑节，不要八节全上**——用不上的节只会稀释注意力。

| 目标 | 用哪几节 |
|---|---|
| 并发 / 事务 / 队列 / 限流 / 定时任务 | 一、二 |
| 认证 / 权限 / 密钥 / 令牌 / 二次验证 | 四、八、三 |
| 前端状态 / 表单 / 弹窗 / 列表刷新 | 二、六 |
| 测试是否可信 | 五 |
| 重构 / 复用 / 改名 / 搬代码 | 七、三 |
| 资金 / 账务 / 支付 / 退款 / 对账 / 汇率 | **九**、一、二 |
| 外部集成 / webhook / 批量导入 / 服务商同步 / ETL | **十**、二、六 |
| 需求对照 | 三 |
| 全面复盘 | 全部，分派子代理 |

## 第三步 · 扫描

- **范围小**（单文件、单次 diff、两三节）→ 自己扫。
- **范围大，或用了 ≥3 节** → **分派子代理**。

**按节切，不要按编号平均切。** 各节要读的材料根本不同：

| 节 | 要读的材料 |
|---|---|
| 五 | 测试代码 |
| 七 | 注释、复用点、历史 |
| 三、四 | 实现 + 需求文档 |
| 一、二、六、八 | 实现代码与分支 |
| 九 | 金额流转全链路（报价→提交→落库→发给服务商→回调→入账）、账本/流水表、DDL 里的 DECIMAL 定义 |
| 十 | 外部集成代码（provider adapter、webhook controller、批量导入解析器、event inbox）、第三方接口文档/契约（有的话）、集成测试 |

按编号平均切会让每个代理都被迫读一遍全部代码。

**每个子代理必须原样带上这段【规则】**，否则它会退回"应该没问题"：

```
- 每个判断都要指出代码位置（文件:行）。指不出来就明说"没有"。
- 确实没有就答"没有，因为X"，不要为了凑答案而编。
- 每个结论标注证据等级：受控复现 / 生产日志 / 局部实验 / 读代码推断。
- 说"概率很低"之前，先回答：对方能不能自己挑时机？
- 每条发现标上问题编号与严重度（严重 / 中 / 低）。
- 只回答分给你的那几节，不要越界。
```

## 第四步 · 汇总

去重，按**严重度**排序（不是按编号顺序）。每条发现给全五项：

```
[编号] 严重度 — 一句话结论 — 文件:行 — 证据等级
```

- 证据等级只到「读代码推断」的，单独归入 **待核实**，不要和已确认的混排。
- 子代理的结论不要照单全收：明显可疑的，自己回去核一眼再报。**尤其是每条「严重」，都要自己回去把那几行贴出来。**
- **复核要独立于原推理，不要顺着它检查。** 核实一条发现时，不要读代理的解释再判断"听起来对不对"——抛开它的措辞，自己重新从代码/DDL/日志里把事实推一遍。独立复核比"沿着已有解释验证"更能挡住幻觉：本次每条「严重」都是这样核过的，没有一条是靠认同代理的说法过关。
- **按"结论形状"去重，不要按文件去重**——按节分派时材料必然重叠（同一段代码在第一节是"读改写覆盖"、在第二节是"快照与实时值分叉"），那是两条不同的结论。
- 每条发现都要能落到一个编号上。**落不上的，就是清单该补的那一条**——把它连同建议措辞一起报出来。
- **扫描目标是 diff / PR 时**，每条发现标注是本次改动**新引入**的还是**改动前就已存在**的（对照改动前的版本或 `git blame`）。价值不同：新引入的通常该卡在合并前；已存在的记录下来但不必阻塞，除非严重度本身够高。

## 第五步 · 计分（不要跳过）

回写 `questions.md` 文末两张表：

1. **扫描日志** 加一行：日期 / 扫描对象 / 用了哪几节 / 命中编号。
   **即使 0 命中也要记** —— 它是分母。没有分母，"0 命中"分不清是"没采样"还是"低价值"。
2. **命中榜**：命中的编号 `+1`，更新最高严重度与最近命中；没建行的建行。

排名看「命中 × 最高严重度」两列，**不要只按次数**——低频高危的问题会被纯次数排名系统性压下去。

## 维护

- 发现一类问题在清单里**找不到归属** → 提议新增。编号取本节下一个没用过的号，**永不复用旧号**；编号是身份不是位置，可按逻辑插在相关问题旁边。
- 新问题必须是**强问法**：要位置、要计数、要反例、要分档，不能是"是/否"能打发的。
- **删除问题必须先跟用户确认**，不要自行删除。条件是同时满足「问过很多次仍 0 命中」且「从未命中过中危以上」。
- 没有条数上限。清单变长就多派子代理，不要为了控长度而删问题。
