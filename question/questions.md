# 提问模板

> **用途**：写代码前贴进 prompt 定调；写完后当自查表；复盘时逐条走。
> **信念**：多数 bug 不是"想到了但写错了"，是"没想到要问这一层"。**问法决定能不能被想到。**
> **纪律**：每条回答都要**指出代码位置**；指不出来就明说"没有"，不接受"应该没问题"。
> **编号**：`T*` 是手法，`N.M` 是问题。**编号永不复用**，删掉即作废；**编号是身份不是位置**，顺序可按逻辑调整。命中记录见文末「计分」。

---

## 通用变换（把弱问法改成强问法）

- **T1 要位置，不要判断** — 不问"有没有问题"，问"谁保证的？把那行贴出来"。
- **T2 把"有没有"换成"有几处"** — 计数强制枚举，枚举强制遍历；"有没有"找到一个正例就收工。
- **T3 问概率，不问可能性** — 先回答"对方能不能自己挑时机"，再谈概率。
- **T4 要能让它变红的那个改动** — 不问"覆盖了吗"，问"把实现改错，哪一行断言会红"。
- **T5 分开"写下来"和"被强制"** — 规则写在哪一层？违反时最早在哪一步被拦住？
- **T6 先问能不能消除，再问怎么测** — 让错误状态无法构造的结构，强过任何检测。
- **T7 给一个说"没有"的出口** — "确实没有就说『没有，因为X』，不要为了凑答案而编。"
- **T8 让它反驳自己** — "这个结论如果错了，最可能错在哪一步？"以及"你定级依据的那句理由，本身成立吗？"

## 一、时序与并发

- **1.1** 这里的"检查"和"依据检查结果动手"是不是两步？中间隔了什么？靠什么保证原子——唯一约束 / CAS / 原子脚本 / 悲观锁 / 什么都没有？
- **1.9** 能不能把"检查"和"动手"合成**一个原子的占坑动作**——先申请额度 / 先插一行 / 先 CAS 改状态，**占坑成功本身就是许可**，而不是先看一眼再决定？占没占上**凭什么判定**：影响行数 / 唯一键冲突 / 返回值，还是又去查了一次（那就退回两步了）？
- **1.10** 占坑之后的动作失败了，**坑还回去吗**？把补偿的那行指出来。不还，会不会把额度或资源永久占死？还了，会不会让"故意失败"变成绕开限制的手段？
- **1.2** 读出一个对象 → 改几个字段 → 整体写回：会不会把"我没改、但别人在这期间改了"的字段一起盖掉？反过来，想把某个字段清空，做得到吗？
- **1.3** 守卫钉在"状态"上还是"过程"上？危险窗口从哪一刻开始——渲染到某一步，还是请求发出那一刻？
- **1.4** 拿到锁之后，锁外读到的东西有没有重新读一遍？
- **1.5** 有没有"先动手、事后刹车"的地方？刹车失败时，已经做掉的那一半怎么办？
- **1.6** 用户点了取消，在途请求会被中止吗？还是界面消失了、副作用照样发生？
- **1.7** 同一个请求重放两次会发生什么？把防重复的那道防线指出来。
- **1.8** 这个竞态是随机的，还是对方可以挑时机的？如果能挑，一天能打多少次、命中率多少？

## 二、数据源与状态

- **2.1** 把这个事实在系统里的**所有表示**列出来，标出各自是什么时候、由谁算出来的。
- **2.2** 屏幕上（/日志里/响应里）的这个值，和系统做决定时用的那个值，是**同一次计算**出来的吗？中间隔了多久，这段时间谁能改它？
- **2.3** 这里存的是**用户点击那一刻的意图**，还是**当前的真实状态**？两者分叉时谁赢？
- **2.4** 这两份能不能**收口成一处**？有没有办法直接用手里已有的真实数据，而不是再维护一个常量？
- **2.5** 这个常量在系统另一端有没有对应的一份？改一端会不会漏另一端？
- **2.6** 这份数据**允许陈旧多久**？先归档再谈实现：**必须实时**（决策 / 资金 / 权限的依据）/ **可以滞后几秒**（列表、计数、统计）/ **无所谓**（装饰性）。默认不是"越新越好"，而是"先把要求说清楚"。
- **2.7** 归到"必须实时"的那些，**刷新由谁触发**——轮询 / 窗口重新聚焦 / 某个用户操作之后 / 服务端推送 / **没有人**？如果这里存的是服务端数据，它的失效机制在哪一行？
- **2.8** 如果它们不同步会怎样？**分三档回答**：① 只是难看 ② **界面在撒谎，用户会据此做出错误决定** ③ 会导致错误的资金或权限动作。第②档最容易被低估——系统行为可能完全正确，但用户是在错误信息下按的确认。

## 三、约束的执行力（写下来 ≠ 被强制）

- **3.1** 这条规则现在写在哪一层——注释 / 文档 / 变量名 / 类型 / 运行时校验 / 数据库约束？
- **3.2** 有人违反它时**最早在哪一步**被拦住：编译期 / 测试 / 启动时 / 运行时 / 永远不会？
- **3.3** 需求里写了、但代码里找不到实现的条目有哪些？**逐条对照**，不要相信"应该实现了"。
- **3.4** 代码注释里"为什么这么做"的那段理由，和需求一致吗？（实现方写下的理由不是设计依据）
- **3.5** 这个约束能不能交给类型系统，让非法状态**根本无法构造**？
- **3.6** 这条规则有几条实现路径？每一条都过同一个关卡吗？绕过的那条会不会**连报错都没有**？
- **3.7** 客户端做的这个检查是安全措施还是引导？绕过它之后，服务端会拦吗？

## 四、凭据、密钥与生命周期

- **4.1** 同一个秘密在不同存储介质里的保护级别一致吗？（一处加密、另一处明文，等于没加密）
- **4.2** 这个存储里哪些是**短命的过程状态**、哪些是**长期凭据**？"反正这里本来就有敏感数据"这句话，拆开看还成立吗？
- **4.3** 这东西创建之后，什么情况下应该作废？**把作废的触发点全部列出来**，逐个对照代码里有没有。
- **4.4** 已经签发出去的凭证，在签发之后主体状态变了（停用 / 删除 / 改密 / 降权），谁来发现？**签发时校验过 ≠ 使用时仍然成立。**
- **4.5** "一次性"是被谁执行的？把执行它的那行代码指出来。
- **4.6** 这个秘密会不会出现在日志、异常信息、`toString`、响应体、URL 里？
- **4.7** 恢复通道（恢复码 / 客服重置 / 备用邮箱）的强度是不是低于主通道？攻击者会走哪条？
- **4.8** 解密或校验失败时，有没有一条"降级"的静默回落路径？有没有一条路能让人在不知道旧密钥的情况下换成新的？

## 五、判据与证据（测试真的在测那件事吗）

- **5.1** 把这段代码里的关键调用**整段删掉**，测试会红吗？
- **5.2** 测试钉的是"调用发生过"还是"调用发生在正确的位置"？把它挪到后面一步，还绿吗？
- **5.3** 断言里的这个值，是从**被测代码**算出来的，还是从**测试的桩**算出来的？
- **5.4** 测试的输入集合能走到那个分界点吗？**把唯一能区分对错的那个输入写出来**，它在集合里吗？
- **5.5** 这条断言/不变量**有没有可能失败**？结构上永远为真的，是负资产，应该删掉。
- **5.6** 测出来的这个上限，会不会是**测试工具自己**的上限？
- **5.7** 缺陷落在单点上还是**状态组合**上？如果是组合，例子测试结构上就够不到——穷举的动作集里有没有"**世界在变**"（服务端被别处改、定时器到期、另一个客户端在操作）？状态空间小到能走完时，别赌随机抽样。
- **5.8** 这个结论是哪一档证据：受控复现 / 生产日志 / 局部实验 / 读代码推断？

## 六、默认值、兜底与未知态

- **6.1** 这个兜底分支（`else` / `default` / 链条末尾）会做什么？如果它是破坏性的，靠什么防守？**"上层碰巧到不了"不算防守。**
- **6.2** 这个布尔量把几种状态压成了两种？"未知 / 加载中"和"已知的另一种"被混为一谈了吗？
- **6.3** 遇到未知值或新增枚举时往哪边倒？**两种说错话的代价对等吗？**
- **6.4** 这条"未知时怎么办"的规则只适用于哪一帧？会不会被套到它不适用的帧上？
- **6.5** 失败时是抛异常还是静默 `return`？上游会把静默 return 当成成功吗？
- **6.6** 一个**错误的正面反馈**，会不会比没有反馈更糟——它是不是把"该去补救"的线索也一并抹掉了？
- **6.7** 输入过滤 / 净化器放行的字符集，和后端实际接受的格式一致吗？

## 七、复用、漂移与文案

- **7.1** 这段代码是从哪儿抄来的？抄的时候里面的**字面量**（标题、提示语、常量、日志前缀）跟着改了吗？
- **7.2** 这条注释**照着做会出事吗**？（比"过时"更严重的是"引向错误改法"）
- **7.3** 有没有"目前只有一个消费者，先放这儿"这类注释？第二个消费者已经出现了吗？
- **7.4** 有没有拿**人类可读的文案**当控制流用？（判断错误信息里有没有某个子串）
- **7.5** 同一个形状在别处还有几处？只修一处，会不会让下一个人以为这个形状没问题？
- **7.6** 两个独立的地方在改同一个东西吗？它们的执行顺序谁定？
- **7.7** 这个 bug 修了一半吗？（这一处区分了，另一处没跟上）
- **7.8** 这次改动里"不在本次范围"的部分是什么？**写下来**，否则三个月后没人记得。

## 八、信任边界

- **8.1** 这个值是谁给的——用户 / 另一个服务 / 我们自己算的？跨边界的那一行有没有重新校验？
- **8.2** 客户端传上来的这个字段，服务端信了吗？如果服务端本来就能自己算出来，为什么还要收？**能不能结构上就不给这个字段？**
- **8.3** 归属 / 租户隔离：这个查询带上归属条件了吗？"不存在"和"存在但不属于你"返回的是同一句话吗？
- **8.4** 这个错误信息会告诉对方他不该知道的事吗？

## 维护约定

**加问题**
- 新 bug 先问：**它属于已有的哪一类？**属于 → 什么都不用加；不属于 → 才考虑加一条新问题。
- 每条新问题必须是**强问法**：要位置、要计数、要反例、要分档，而不是能用"是/否"打发的。
- 发现一个"换个问法就问出来了"的时刻，去补 `T*` 通用变换——那里比问题清单更值得投入。

**计分**
- **编号永不复用。** 删掉一条，它的编号一并作废，新问题取本节下一个没用过的号。否则历史计数会张冠李戴。
- **只有真的发现了问题才 +1。** 扫了没发现，不计；发现的是已知问题，照样计——它证明这一问有鉴别力。
- **同时记严重度，不只记次数。** 低频高危的问题（凭据、越权、资金）会被纯次数排名系统性地压下去，而那恰恰是最不该删的一类。
- **每次扫描都要登记用了哪几节**，否则"0 命中"无法区分"没采样"和"低价值"。

**规模与删除**
- **没有硬性条数上限。** 问题越攒越多是好事——它意味着采样面在变宽。为守上限而删掉的，恰恰是还没攒够数据的那些。
- 一次扫不完就**分派子代理**，**按节切，不要按编号平均切**：同一节共享材料（五要读测试，七要读注释与复用点，三、四要对着需求读，一、二、六、八读实现与分支），混装会让每个代理都被迫读一遍全部代码。
- 每个子代理都要带上【规则】那四行，否则它会退回"应该没问题"。各自只报自己那几节的编号与严重度，主会话汇总去重。
- **删除是例外，必须先跟我确认。** 只有同时满足「被问过很多次仍 0 命中」**且**「从未命中过中危以上」才提出来问，**不要自行删除**，也不要凭印象删。
